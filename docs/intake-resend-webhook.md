## Behavior and evidence boundaries

`POST /api/intake-resend-webhook` accepts only signed Resend events. Both the production environment flag and a separate private database switch must permit writes. Vercel previews, deployment aliases, and local preview servers cannot write using this production handler. Only the exact `hammadmedia.com` host is accepted.

Resend's successful send response already establishes **provider acceptance** in `submissions.email_state`. This webhook records independent provider-reported events. `email.delivered` means the recipient's mail server accepted the email; it does not prove inbox placement, forwarding, opening, or human receipt. `email.bounced`, `email.failed` and `email.suppressed` identify different negative outcomes. Spam complaints remain an attention flag even when delivery was reported. The existing browser receipt still means durable inquiry acceptance, irrespective of subsequent email delivery. [Resend event definitions](https://resend.com/docs/webhooks/event-types), [delivery semantics](https://resend.com/docs/webhooks/emails/delivered).

The event ledger contains only the Svix event ID, Resend email ID, allowlisted event type, event/receipt timestamps, raw-payload SHA-256 and a conflict flag. It excludes the raw payload, email addresses, subject, body, diagnostic text, tags, links and inquiry data. The request body is held transiently for verification, capped at 64 KiB, and never logged. Minimal event identifiers/facts are retained for durable replay prevention and delivery reconciliation, like the existing receipt tombstones; the 30-day inquiry-body cleanup does not erase them. Review retention and storage usage operationally before adding any new fields or indefinite high-volume traffic.

Only events whose sender is `intake@notifications.hammadmedia.com` and whose sole recipient is `contact@hammadmedia.com` are eligible. Display-name wrapping of the exact sender address is supported. Other sender/recipient pairs and opened/clicked/domain events are authenticated then ignored. This is intentionally a single-recipient operational notification integration.

An event can arrive before the worker saves its `email_id`. Its minimal facts are retained and join automatically once that exact provider ID exists. No matching by contact address, subject, brand, or guessed inquiry is permitted. Unmatched messages are excluded from inquiry delivery counts; they may be early events, operations notices or other messages using the same sender. Operations-notification delivery is not included in this inquiry projection.

Arrival order never overwrites prior facts. Sent/delayed events cannot regress delivered/bounced evidence. Delivered plus a negative terminal event produces `conflicting`, with all facts preserved for review. Reusing one Svix ID with different content returns 409 and persists a conflict flag. Repeated identical deliveries return 200 without new rows or a fresh event timestamp. Multiple inquiries sharing one provider ID also become conflicting. No delivery event changes `email_state`, Notion Stage/Status, sticky ownership, no-chase, CRM records, lease state, or resend eligibility.

## Security and deployment configuration

Verification follows Svix's documented HMAC-SHA256 `id.timestamp.rawBody` format, a five-minute past/future attempt tolerance, versioned signature-list handling and constant-time digest comparison. Tests include Svix's published independent vector. JSON is parsed only after authentication. The handler reads original byte-stream events, never `req.body` or reserialized JSON. The current Vercel Node runtime restores the raw stream when attaching its lazy body helper; a regression fixture covers that behavior. Do not replace this with an Express/Next body parser or global runtime setting without a new raw-byte integration check. [Resend verification](https://resend.com/docs/webhooks/verify-webhooks-requests), [Svix manual specification](https://docs.svix.com/receiving/verifying-payloads/how-manual), [Vercel runtime implementation](https://github.com/vercel/vercel/blob/main/packages/node/src/serverless-functions/helpers.ts).

No SDK or additional dependency is installed. No new Supabase project, privilege tier, or paid service is required by the code. Each accepted event needs one bounded database RPC and a small ledger record; repeated attempts add function/DB usage. Existing plans have usage limits, so this is not a promise of zero incremental charges. There is no polling schedule or email-volume increase from the webhook.

## Aggregate contract

`public.hm_intake_resend_health()` returns counts, the database switch and the last newly recorded event time. It returns no row contents or identifiers. `database_enabled` is only a configuration flag, not proof that the deployed endpoint or provider subscription works. `last_recorded_at` is event activity, not a periodic heartbeat; inactivity alone is not a failure. Missing historical events remain unknown.

Counts are per distinct provider message linked to retained intake submissions, including labeled preview tests already in that outbox. They are not production-only lead counts or business-conversion statistics. `delivery_reported_messages` preserves positive provider facts even when conflicting negative evidence also exists; consult `conflicting_messages` and `attention_messages`, not that number alone. `delivery_unconfirmed_messages` excludes messages with recorded positive or negative terminal evidence. Failure, complaint and conflict counts can overlap. Never sum them as distinct inquiries.

Use the private view for authorized manual diagnosis only. Owner-only CRM integration should display provider acceptance, mail-server delivery, unknown and attention distinctly and should not expose identifiers, raw provider errors or public GA tracking. This webhook does not silently change the existing watchdog health or enable new alerts; incorporating delivery attention in an alert rule requires its own reviewed acceptance criteria.

## Disable and rollback

Set the private database enable switch false first to stop new ledger writes even if a previous deployment is still running. Disable the Resend endpoint and set the production flag false in the coordinated rollback. Keep stored event facts and inquiry receipts; do not delete them to force a resend or clear attention. The 503 response deliberately prevents false successful acknowledgement, but provider retries are finite, so record the downtime and reconcile/replay missed provider events after recovery. A design rollback must retain the receiver URL and worker, or explicitly pause the provider subscription and document the evidence gap.

Existing inquiry processing can continue while event reception is paused. Status then means unknown/stale event coverage, never confirmed delivery. Do not turn on the watchdog, Cron, automatic email, Notion writes, or a new lead qualification flow as part of this endpoint's activation.
